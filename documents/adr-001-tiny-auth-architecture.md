# ADR-001: Архитектура микросервиса tiny-auth, границы RBAC и контракт интеграции в режиме Emergency Brake

## Статус
Принято (Approved) — Апрель 2026 г.

## Контекст
В ходе разделения монолита на изолированные домены потребовалось спроектировать доверенный периметр безопасности (IAM). Были выдвинуты жесткие требования со стороны информационной безопасности (ИБ) и системных инженеров:
1. **Изоляция учетных данных:** исключить размытие паролей, сессий и криптографических ключей по бизнес-сервисам.
2. **Экстренное реагирование (Emergency Brake):** ИБ должна иметь возможность мгновенно отозвать доступы компрометированного аккаунта на уровне ядра авторизации, минуя кадровые цепочки.
3. **Производительность авторизации (High Load):** проверка прав на gRPC-интерцепторах и API Gateway должна выполняться за наносекунды криптографическим методом, без сквозных синхронных запросов в БД при каждом клике.
4. **Административная гибкость:** управление ролевой моделью должно быть доступно как машинам внутри сети (gRPC), так и инженерам через административную панель (REST).

## Решение

### 1. Архитектурная модель данных (RBAC)
Внутри изолированной базы данных `tiny-auth` реализуется классическая реляционная схема контроля доступа на основе ролей (**RBAC** — Role-Based Access Control) по схеме «многие-ко-многим»:
* **`users`**: `id` (UUID), `login` (email/phone), `password_hash`, `status` (active/blocked/deleted), временные метки (`created_at`, `updated_at`).
* **`roles`**: `id` (INT/UUID), `name` (уникальный ключ, например: `"admin"`, `"employee"`, `"manager"`), `description`.
* **`user_roles`**: связующая таблица с составным первичным ключом `(user_id, role_id)`, инкапсулирующая пересечение доступов.

### 2. Интерфейсы взаимодействия (Полиморфизм транспорта)
Реализовать полный набор CRUD-операций для всех трех внутренних сущностей (`User`, `Role`, `UserRoles`) через двойной транспортный слой:
* **REST API:** Публичный контракт для административной панели ИБ. Используется человеком для ручного аудита, заведения новых системных ролей и экстренной блокировки.
* **gRPC API:** Внутренний контракт для автоматизации «машина-машина». Используется другими микросервисами (например, автоматическое добавление роли `employee` кадровым сервисом при завершении онбординга).

### 3. Механика сессий и Emergency Brake (Экстренный тормоз)
* Сервис является единственным эмитентом короткоживущих **JWT-токенов**. В Payload токена зашивается строго необходимый минимум: `user_id` и плоский массив `roles` (из `UserRoles`). Выдача токена может быть расширена вторым фактором (**OTP**) через Redis-кэш без вовлечения бизнес-БД.
* В случае компрометации аккаунта, `tiny-auth` выступает в роли **Emergency Brake**. При переводе пользователя в статус `blocked` (через gRPC/REST) сервис мгновенно публикует высокоприоритетное событие `auth.user.blocked` в шину **Apache Kafka** (с ключом `user_id`).
* Потребители этого события (API Gateway, `tiny-profile-service`) обязаны мгновенно занести `user_id` в черный список сессий в Redis и стереть мобильные push-токены, полностью аннулировав доступ во всем контур приложения.

## Последствия

### Плюсы
* **Абсолютная безопасность учетных записей:** Пароли и роли не покидают периметр безопасности `tiny-auth`. Другие сервисы валидируют JWT автономно по открытому ключу.
* **Независимая блокировка:** Технический доступ (`User`) может быть заблокирован мгновенно на уровне ядра ИБ, даже если кадровый статус сотрудника (`Person`) в системе `tiny-profile` все еще числится как активный.
* **Симметрия API:** CRUD-методы полностью закрывают потребности как ручной, так и программной интеграции.

### Минусы / Риски
* **Сложность каскадного удаления:** При полной ликвидации пользователя (Soft Delete) требуется скоординированная работа консьюмеров Kafka во внешних сервисах (`tiny-profile` и `tiny-person`) для очистки кэша данных.
