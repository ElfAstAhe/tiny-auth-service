# ADR-003: Архитектурный дизайн REST API ядра безопасности tiny-auth-service и стратегия Code-First для OpenAPI

## Статус
Принято (Approved) — Сентябрь 2026 г.

## Контекст
В соответствии с системной архитектурой [ADR-002] микросервис `tiny-auth-service` обязан предоставлять полиморфный интерфейс взаимодействия. Помимо внутреннего gRPC-слоя для межсервисных коммуникаций, требуется спроектировать REST API контур.

К REST API предъявлены следующие требования:
1.  **Административный контроль:** обеспечение удобного человеко-читаемого интерфейса для Frontend-панели ИБ.
2.  **Изоляция сетевых контрактов:** структуры REST-ответов должны быть очищены от служебных полей Protobuf, отдавая фронтенду чистый, валидный JSON.
3.  **Гибкость HTTP-семантики:** возможность управления честными REST статус-кодами (например, `200 OK`, `201 Created`, `401 Unauthorized`), которые сложно маппить через автоматические gRPC-шлюзы.
4.  **Синхронизация документации (Day-2 Operations):** исключить ручное написание файлов `openapi.yaml/json` для предотвращения рассинхронизации документации с реальным кодом бэкенда.

## Решение

### 1. Транспортный слой и Маршрутизация (Routing Layer)
*   Контур REST API реализуется как независимый программный слой на базе легковесного, идиоматичного для Go роутера **`go-chi/chi/v5`**.
*   gRPC-сервер и REST-роутер `chi` разделяют общие доменные юзкейсы (Use Cases) на уровне бизнес-логики, но полностью регистрируются и настраиваются отдельно.

### 2. Стратегия Code-First для OpenAPI (Swagger)
*   **Принцип Single Source of Truth на уровне Go:** Генерация OpenAPI-спецификации (Swagger) переносится на уровень исходного кода Go. Документация парсится автоматически из декларативных комментариев (аннотаций) к обработчикам (Handlers) и DTO-структурам с помощью встроенного в CI/CD тулинга (`swaggo/swag`).
*   Результирующий Swagger-файл встраивается прямо в бинарный файл микросервиса (через `embed`) и отдается встроенным HTTP-обработчиком для нужд дебага и Day-2 эксплуатации инженерами.

### 3. Карта эндпоинтов и HTTP-маппинг

Все эндпоинты изолированы внутри роутера в общем неймсейсе `/api/v1` и разделены по контурам окружения:

#### 3.1 Системный контур и Отладка (System & Diagnostics)
*   `GET /healthz` — Проба жизнеспособности (Liveness Probe).
*   `GET /readyz` — Проба готовности к приему трафика (Readiness Probe).
*   `GET /config` — Выгрузка текущей конфигурации приложения (**Доступно только в Non-Production окружениях**).

#### 3.2 Контур Аутентификации (Public Auth API)
*   `POST /api/v1/auth` — Обмен пары логин/пароль на JWT сессию (`token` + `refresh_token`).
*   `POST /api/v1/auth/simple` — Упрощенная легковесная аутентификация (**Доступно только в Non-Production окружениях**).

#### 3.3 Контур Пользовательского Самообслуживания (User Self-Service API)
*   `GET /api/v1/users/profile` — Получение данных текущего авторизованного профиля.
*   `POST /api/v1/users/register` — Самостоятельная регистрация аккаунта (**Доступно только в Non-Production окружениях**).
*   `PUT /api/v1/users/password` — Изменение пароля текущего пользователя.
*   `PUT /api/v1/users/keys` — Генерация/обновление криптографических пар ключей пользователя.

#### 3.4 Административный контур Пользователей (Admin Users API — Защищенный контур ИБ)
*   `GET /api/v1/admin/users/{id}` — Точечный поиск пользователя по UUID.
*   `GET /api/v1/admin/users/search` — Бизнес-поиск/фильтрация пользователей по query-параметрам.
*   `GET /api/v1/admin/users/` — Пагинированный список всех пользователей системы.
*   `POST /api/v1/admin/users/` — Создание новой учетной записи.
*   `PUT /api/v1/admin/users/{id}` — Полная модификация/обновление данных пользователя по ID.
*   `DELETE /api/v1/admin/users/{id}` — Инициация процедуры каскадной дезактивации (Soft Delete).

#### 3.5 Административный контур Ролевой Модели (Admin Roles API — Защищенный контур ИБ)
*   `GET /api/v1/admin/roles/{id}` — Точечный поиск роли по ID.
*   `GET /api/v1/admin/roles/search` — Бизнес-поиск ролей по query-параметрам (например, по имени).
*   `GET /api/v1/admin/roles/` — Получение полного списка ролей в системе.
*   `POST /api/v1/admin/roles/` — Создание новой системной роли.
*   `PUT /api/v1/admin/roles/{id}` — Изменение параметров существующей роли.
*   `DELETE /api/v1/admin/roles/{id}` — Удаление роли из RBAC-матрицы.

### 4. Контекст Безопасности (Security Context)
*   Все эндпоинты контуров `/api/v1/users/*` и `/api/v1/admin/*` защищаются соответствующими middleware-компонентами авторизации.
*   В коде обработчики в обязательном порядке размечаются аннотацией `@Security BearerAuth`.

## Последствия

### Плюсы
*   **Безопасность Production-окружений:** Жёсткое ветвление роутера (`if Env != Production`) на уровне компиляции/инициализации гарантирует, что ручки регистрации (`/register`), упрощенного входа (`/auth/simple`) и дампа конфигов (`/config`) физически отсутствуют на боевых серверах, полностью исключая данный вектор атак.
*   **Чистота REST-семантики:** Четкое разделение на `POST` (создание), `PUT` (полное обновление ресурса по ID/пути) и `DELETE` соответствует каноническому стандарту RESTful API.
*   **Гибкость поиска:** Использование `/search` эндпоинтов позволяет расширять критерии фильтрации (по логину, статусу, дате создания) через query-параметры без изменения путей роутинга.
